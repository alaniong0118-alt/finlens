# Data Freshness review fixes

Status: completed (bounded repair implementation; independent re-review pending)
Roadmap phase: bounded repair of Data Freshness & Automatic Refresh

## Objective
Resolve the four independently reproduced P2 findings: displaced publication,
uncertain commit reporting, continuation after fatal checkpoints, and catalog
reconciliation lost after a transient failure.

## Current architecture and context
Reuse the [implementation plan](2026-10-08-data-freshness-automatic-refresh.md)
and [runbook](../../data-freshness.md). Starting tree: 30 modified tracked files,
16 untracked files, nothing staged. Preserve all work and generated next-env bytes.

## Constraints and non-goals
No SEC/OpenAI calls, development writes/migration, scheduling, dependency changes,
financial selector/arithmetic changes, staging, commits, or unrelated features.
All write verification uses disposable databases. Operational rollout stays pending.

## Implementation stages
1. Bind refresh publication transactions to the admission-owning PostgreSQL connection.
2. Reconcile uncertain commits from a new connection; represent unknowable counters as null.
3. Stop later streams immediately after fatal checkpoint/database outcomes.
4. Acknowledge catalog reconciliation only after successful fetch/state application.
5. Add permanent failure regressions, run focused mutations and required validation,
   verify development fingerprints, and update reports/runbook.

## Decisions
- Use the existing session advisory lock and its connection for refresh publication;
  a second ownership check alone cannot close the loss-before-commit window.
- Preserve the existing durable attempt as the authority after uncertain commit.
- Retry catalog reconciliation on subsequent bounded freshness checks, not immediately.

## Discovered issues
The independent review reproduced all four defects. Its findings are the bounded
repair scope; no new milestone or operational activation is authorized.
The mounted regression also required retaining question text across the first
filing remount; text moved to company state without weakening result invalidation.
An initial parallel mutation run exposed an overly broad test advisory-lock PID
lookup. It now filters the current disposable database and uses a lock timeout.
Final sequential mutation runs detected the intended financial/reporting failures.

## Final outcome
All four bounded repairs are implemented. Refresh publication uses the lock-owning
connection; a lost connection cannot publish. A fresh read connection establishes
the finished transaction/ledger outcome, preserving confirmed commits and exposing
unknown outcomes with null committed counts. Fatal report/database errors prevent
later streams. Catalog reconciliation acknowledges successful application only,
retries on later checks and rejects aborted/old-company responses.
